# 企微私域用户分层工具决策记录

## 已确定

| 结论 | 理由 |
| --- | --- |
| 项目目标是根据企微聊天内容自动更新用户分层，并同步到运营可用的表格。 | 用户希望减少从聊天中提取信息、更新分层和维护运营表格的手工工作。 |
| 采用深挖强度规划，并持续记录结论和理由。 | 用户希望在确定方案前检查关键假设、风险和边界情况，并保留决策依据。 |
| 从当前工作区重新开始，在本地 `main` 建立新的初始提交。 | 用户要求删除此前的 Git 记录，重新开始项目。 |
| 首版的核心交付是自动生成并更新用户分层数据表。 | 当前验证重点是聊天内容能否转成可用的分层数据，使用岗位不影响首版范围。 |
| 用用户自己的企微成员账号做单账号试点，覆盖员工与客户私聊。 | 用户希望先在自己的账号上验证从私聊到分层表格的链路。 |
| 首版围绕高中在线教育的招生转化设计，覆盖来自抖音和小红书的自然流线索。 | 分层需要服务从线索承接到付费的业务流程，关注有效线索率、试听转化率、付费转化率和 GMV。 |
| 单纯领取资料不计入有效线索。 | 领取资料本身不足以判断用户有具体学习需求。 |
| 首版仅依据企微私聊分层，试听到课和付费只在出现相关信号时标记待核实。 | 首版没有课程或订单数据可供交叉验证。 |
| 首版同步目标为飞书多维表格。 | 用户指定先按飞书继续规划。 |
| 按 [首版方案](./plan-wecom-segmentation.md) 推进，先验证离线分层，再验证飞书同步，最后接入可用的企微会话存档。 | 用户已确认首版方案。按此顺序可以独立验证分层和同步，并在存档可用后测试真实采集。 |
| 首版部署到用户自己的 Mac，由用户一人使用。 | 单人试点可直接利用现有设备，减少部署和维护工作。 |
| 优先降低持续成本。 | 用户仅供个人使用，希望控制日常开支。 |
| 采用方案 A。首版用 Python 3.13 编写本地命令行任务，用 SQLite 保存处理进度、去重记录和同步重试状态，用飞书多维表格作为日常操作界面。 | 单人试点可在现有 Mac 上运行，SQLite 足以保存同步所需状态，无需单独维护数据库服务。 |
| 在 Mac 上以本地模式运行 Ollama，从 `qwen3:4b` 开始验证。模型按结构化格式提取聊天事实，Python 规则判定分层，飞书保存结构化结果和脱敏证据摘要。 | 用户选择本地分析方案，可在本机验证提取质量，并避免模型按量计费。分层规则可以独立测试。 |
| 首轮从手动命令触发，后续有定时需求时使用 macOS 的 `launchd`。 | 同一条命令可用于样本回放和后续定时执行，先验证处理结果再确定运行频率。 |
| 方案 A 的模块边界、数据结构、同步和验收见 [技术方案](./technical-design-wecom-segmentation.md)。 | 技术方案将已选框架落实到导入、提取、分层和飞书写入，明确样本验证和真机联调的依赖。 |
| 为本机操作增加 SwiftUI 原生 macOS 工作台，通过进程管道调用现有 Python 分层和同步逻辑。 | 用户指定本地软件形式。项目已使用 Swift 编译企微窗口读取程序，可用同一套构建工具生成 `.app`，同时保留 SQLite、模型和飞书配置。 |
| 日常分层默认使用本机 Ollama，保留 DeepSeek API 选项。 | 当时同一批 50 份合成会话中，修复后的本机模型有 50 份全部关键字段匹配，耗时 255.2 秒。此前 DeepSeek 对照有 49 份全部匹配，耗时 412.5 秒。计时仅覆盖分层流程。 |

## 用户基本情况

| 结论 | 理由 |
| --- | --- |
| 工作台分层预览和飞书多维表格添加文本栏「用户基本情况」。 | 在分层和跟进时都可以快速了解学生学情。 |
| 只汇总客户明确提及的省市、实际年级、近期成绩、薄弱科目和当前学习困难。没有可用信息时留空，摘要排除联系方式和详细地址。 | 用可追溯的学情支持跟进，避免把猜测或个人联系信息带进摘要。 |
| 同一会话出现新学情时更新原飞书行。飞书栏位与工作台上次写入的内容不同（包括手动清空）时，保留飞书内容。 | 自动汇总能跟随新消息更新，运营仍可在飞书保留自己的修改。 |

本栏暂无待定事项。

## 运营模拟验收

使用合成会话、本机 Ollama 和独立的真实飞书数据表验收，便于复现新增、原行更新和手填保护，又能隔离日常记录。验收保留原生界面截图和结果，尚待确认的业务口径集中记录在[运营模拟验收报告](./运营模拟验收.md#需要确认的业务口径)。

首次可采集一问一答。双方已约定试听但相对日期无法核实时，跟进标为「预约时间待确认」，保留客户确认原话，跨天继续待确认。普通未约线索跨天转为暂缓后显示「待更新」，由运营同步原行。

- 后续若接入可核实的到课和订单记录，再确定实际试听、付费转化率及 GMV 的统计口径。
